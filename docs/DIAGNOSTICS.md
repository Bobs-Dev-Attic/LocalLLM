# Diagnostics and Processing Details

## Status and scope

This document specifies an observability feature for LocalLLM, an Android chat client that connects to LM Studio over a user's local network. It is a design specification, not a claim that the current repository already implements these capabilities.

The repository was inspected before this document was added. At that point it contained a minimal README and no Android application source, build files, or existing diagnostics implementation. Treat the architecture below as a target design and adapt names and APIs to the actual application when its source is added.

## Goals

- Make each response's processing path understandable without overwhelming the normal chat experience.
- Help users distinguish model-generation latency from connection, server, and client-side delays.
- Capture enough structured metadata to diagnose failed, slow, interrupted, or malformed requests.
- Keep diagnostics lightweight, bounded, and safe for a privacy-first local application.
- Avoid coupling diagnostics to Compose/UI code or to LM Studio-specific response formats.
- Represent unavailable telemetry honestly; never infer or fabricate token counts, timing, or server internals.

## UX

### Per-message Processing Details

Add a compact details affordance to each assistant response. Keep it collapsed by default and accessible from the message actions area. The expanded panel should group information:

**Request**
- Selected backend and configured endpoint (show a user-friendly host/port; never show credentials or authorization headers).
- Model identifier returned by the server, plus the requested model when they differ.
- Request start time and elapsed duration.
- Request/correlation ID generated by the client.

**Generation**
- Time to first token (TTFT), measured from request dispatch to the first successfully decoded content token.
- Total time to completion, measured with a monotonic clock.
- Prompt and completion token counts only when supplied by the server or reliably measured by a documented tokenizer.
- Generation throughput only when completion-token count and generation interval are both known. Label the calculation and interval.
- Finish reason, such as stop, length, or tool-related completion, when provided.
- Prompt evaluation, generation, context-window, and model-load metrics only when the backend exposes them.

**Outcome**
- Completed, cancelled by user, timed out, disconnected, HTTP failure, protocol/parse failure, or unknown.
- HTTP status and safe server error summary when available.
- Retry count and whether a retry was attempted.

Use an explicit “Not reported by server” or “Not measured” value for unavailable fields. Do not show zero for missing data. Explain that timings are client-observed and may include network and scheduling overhead.

### Live progress

While a response is streaming, show a subtle elapsed timer and a clear state (connecting, waiting for first token, receiving, finalizing). Do not make token-by-token diagnostics noisy or cause list recomposition on every low-level event. Batch UI updates at a modest cadence and keep streaming rendering responsive.

### Diagnostics screen

Provide a dedicated, searchable diagnostics view with:
- Recent request lifecycle events and timestamps.
- Filters for severity, request ID, backend, and outcome.
- A request detail view with safe metadata and sanitized errors.
- Copy/export for support and debugging.
- A clear action and a configurable retention limit.

The normal chat UI must remain useful when diagnostics are disabled or unavailable.

## Event model

Use a structured, versioned event model. Suggested fields:

| Field | Meaning |
|---|---|
| schemaVersion | Version of the diagnostic event schema |
| eventId | Unique event identifier |
| requestId | Client-generated ID shared by all events for one generation |
| conversationId | Optional opaque local identifier; omit from exports by default |
| timestampUtc | Wall-clock timestamp for display and cross-event correlation |
| elapsedMs | Monotonic elapsed time from request start |
| backendId | Stable backend type, e.g. lm-studio |
| endpointLabel | Sanitized host/port or user-defined label |
| modelRequested | Requested model ID, if known |
| modelResolved | Model ID reported by backend, if known |
| eventType | request_started, connection_succeeded, first_token, stream_chunk, completed, cancelled, failed, retry_started |
| outcome | Normalized terminal outcome, when applicable |
| httpStatus | HTTP status, if received |
| durationMs | Duration for a completed operation |
| ttftMs | Time to first decoded content token |
| promptTokens / completionTokens | Nullable measured or server-reported counts |
| finishReason | Backend finish reason, if provided |
| errorCode | Stable client-side error category |
| errorSummary | Sanitized, bounded human-readable description |

Use nullable fields for unavailable values. Keep event types and error categories stable and documented. Do not persist raw streaming chunks as diagnostic events.

## Measurement rules

1. Use a monotonic clock (for example, Android elapsed realtime or a monotonic JVM clock) for durations. Wall-clock timestamps are for display only.
2. Define request start at the point the client begins dispatching the HTTP request.
3. Define connection success according to the HTTP client's observable lifecycle; do not imply it measures TCP/TLS internals unless the client exposes those callbacks.
4. Define TTFT as request-dispatch to first successfully decoded non-empty assistant content. If the stream ends without content, TTFT is unavailable.
5. Define total duration as dispatch to terminal completion/failure/cancellation.
6. Define generation throughput as completion tokens divided by the explicitly stated generation interval. Do not divide by total request duration unless that is the chosen, clearly labeled metric.
7. Prefer backend-provided token counts and performance metrics. If client-side tokenization is added, identify the tokenizer and model compatibility; otherwise omit token counts.
8. Keep separate metrics for queue/wait time, HTTP setup, first token, and stream duration only when the implementation can measure each boundary accurately.
9. Record model-load or prompt-evaluation durations only if LM Studio's API/version provides them. The OpenAI-compatible chat completion stream does not guarantee every LM Studio performance field.

## Architecture

Keep diagnostics independent from presentation and backend-specific parsing:

```text
Compose UI
   |
ViewModel / UI state
   |
Chat use case / orchestration
   +---------------------> Diagnostics service
   |
Backend interface
   |
LM Studio adapter (OpenAI-compatible HTTP + SSE)
```

Suggested responsibilities:

- **Chat orchestration:** creates request IDs, starts/stops timers, coordinates cancellation and retries.
- **Backend interface:** exposes normalized stream events and a typed terminal result; does not depend on Android UI types.
- **LM Studio adapter:** handles endpoint discovery/configuration, HTTP, SSE parsing, response normalization, and backend-specific optional telemetry.
- **Diagnostics service:** accepts structured events, applies redaction and retention, and exposes query/export operations.
- **ViewModel:** maps domain diagnostics to UI state; must not own network instrumentation or raw log storage.

Keep the backend abstraction open to future Ollama, llama.cpp server, or other OpenAI-compatible providers. Represent backend capabilities explicitly (for example, supportsTokenUsage, supportsModelList, supportsPerformanceMetrics) rather than assuming all providers expose the same fields.

## Failure and resilience coverage

Capture, with one request ID:
- Endpoint resolution and connection failures.
- HTTP non-success responses, including status and sanitized error category.
- Invalid JSON, malformed SSE frames, unexpected stream termination, and empty responses.
- User cancellation, app lifecycle interruption, read timeout, connect timeout, and retry.
- Model unavailable, model mismatch, context-length rejection, and server busy errors when identifiable.
- Response completion and finish reason.

Do not automatically retry non-idempotent or partially streamed generations without a deliberate policy. If retry is supported, clearly indicate that a new generation was started and avoid silently concatenating two attempts.

## Privacy and security requirements

Local-first does not mean risk-free. Diagnostic exports may reveal private network topology, model names, usage patterns, and potentially conversation content.

**Safe defaults**
- Never log prompts, generated text, images, audio, files, or tool payloads by default.
- Never log API keys, bearer tokens, passwords, cookies, authorization headers, or full request headers.
- Redact URL user-info, query parameters, and fragments. Prefer a sanitized endpoint label over a full URL.
- Do not persist raw HTTP request/response bodies in ordinary diagnostics.
- Store only the minimum metadata needed to debug a request.
- Make content logging a separate, explicit, off-by-default opt-in with a clear warning and a visible active indicator.
- If content logging is implemented, use short retention, local-only storage, explicit deletion, and exclude content from automatic exports unless the user separately chooses it.
- Exports should be previewable, sanitized, and user-initiated. Warn before sharing logs externally.
- Avoid logging stable device identifiers, precise location, contact data, or unrelated Android system state.
- Do not send telemetry to a developer-controlled service without separate, informed opt-in.

**Network security**
- Prefer HTTPS when the configured server supports it; document the trust model for self-signed certificates rather than disabling certificate validation.
- For HTTP on a trusted LAN, scope any Android cleartext exception narrowly to the user-configured endpoint where platform policy allows. Do not enable global cleartext traffic.
- Treat LAN endpoints as untrusted input: validate scheme/host/port, prevent malformed URLs, and do not follow redirects to unexpected hosts with credentials.
- Avoid exposing the LM Studio server to the public internet. Explain that LAN reachability and firewall/router configuration are the user's responsibility.
- Do not assume a private IP address is trustworthy; a hostile device on the same network may still be present.

## Storage, performance, and lifecycle

- Use bounded storage (for example, a configurable maximum number of recent requests or a fixed age limit); define eviction behavior.
- Store structured metadata, not an unbounded text log.
- Perform persistence and export off the main thread.
- Batch high-frequency stream events; store first-token and terminal milestones rather than every token/chunk.
- Ensure diagnostics cannot block token delivery or cause generation cancellation.
- Use cancellation-safe finalization so every started request receives a terminal state when possible.
- Handle process death as an interrupted/unknown request on next launch; do not mislabel it as a server failure.
- Provide a clear-all operation and tests proving deletion.
- Consider encrypted app-private storage if the selected fields or optional content logs warrant it; encryption does not replace data minimization.

## Accessibility and usability

- Make the details control reachable by screen readers with a descriptive label.
- Use text labels in addition to colors/icons for status.
- Format durations and token rates consistently; support copying raw numeric values.
- Keep error summaries actionable and avoid exposing stack traces in the normal chat view.
- Provide a separate advanced view for sanitized exception details and stack traces.

## Testing and acceptance criteria

- Unit tests verify timing boundaries, null/missing metrics, token-rate calculations, redaction, event ordering, and terminal-state mapping.
- Stream tests cover delayed first token, multiple chunks, empty stream, malformed SSE, premature EOF, cancellation, and server error frames.
- Integration tests cover LM Studio reachable/unreachable, wrong port, invalid model, HTTP errors, timeout, and model switching.
- Privacy tests assert that prompts, completions, authorization values, and sensitive URL components never appear in default logs or exports.
- Storage tests verify retention bounds, process-restart behavior, and clear-all deletion.
- Performance tests confirm event capture does not block streaming or main-thread rendering.
- UI tests verify collapsed-by-default details, accessible labels, missing-metric copy, live progress, and export confirmation.

A feature is ready when the above behaviors are implemented and tested, unavailable backend telemetry is accurately represented, and default diagnostics contain no conversation content or credentials.
